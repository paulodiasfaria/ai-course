Para onde vai a memória da GPU

Na inferência, a memória da GPU tem dois grandes consumidores:

  • Pesos: número de parâmetros vezes bytes por parâmetro. Um modelo de 7 mil milhões em bf16 (2 bytes) ocupa ~15 GB; a 4 bits, ~4 GB.
  • KV cache: para não recalcular a atenção sobre todo o texto a cada token, o modelo guarda as chaves e os valores de cada token já processado, em cada camada. Cresce com o comprimento do contexto e com o número de pedidos em simultâneo. Por token: 2 × camadas × dimensão KV × bytes.

A geração tem duas fases com perfis diferentes. O prefill processa o prompt todo de uma vez (limitado pelo cálculo) e determina o tempo até ao primeiro token (TTFT). O decode gera um token de cada vez (limitado pela largura de banda da memória, porque lê todos os pesos para cada token) e determina o tempo por token. Servir vários pedidos em lote aproveita cada leitura dos pesos para vários pedidos: é daí que vem o ganho dos servidores de inferência.

KV cache em bf16, 90 % da memória disponível para o servidor. A reserva estática guarda o contexto máximo para cada pedido; com PagedAttention os blocos são atribuídos à medida, aqui assumindo que os pedidos usam em média 30 % do contexto máximo.

Quantização: FP8, AWQ, GPTQ e GGUF

Quantizar é guardar os pesos (e às vezes as ativações) com menos bits. Os métodos diferem em como escolhem as escalas para perder o mínimo:

FormatoBitsComo funcionaOnde se usa
FP88 (pesos e ativações)Escala por canal ou por token, sem dados de calibração; perda quase nulaGPUs recentes (H100, L4, RTX 40xx) com vLLM e SGLang
GPTQ4 (às vezes 3 ou 8)Quantiza camada a camada e corrige o erro com informação de segunda ordem, usando dados de calibraçãoGPUs, vLLM; formato W4A16 do llm-compressor
AWQ4Protege os canais de pesos mais importantes para as ativações, com calibraçãoGPUs, vLLM
GGUF (k-quants)2 a 8, por exemplo Q4_K_MBlocos com escalas próprias, pensados para CPU e Apple Siliconllama.cpp, Ollama, LM Studio

Regras práticas: 8 bits quase nunca se nota; 4 bits costuma perder pouco em modelos de 7 mil milhões ou mais, mas modelos pequenos são mais sensíveis; abaixo de 4 bits a qualidade cai depressa. Mede sempre na tua tarefa, com o conjunto de teste do módulo 11, porque os benchmarks gerais escondem perdas em tarefas estreitas como extrair números de encomenda.

Servidores de inferência: vLLM, SGLang e companhia

Um ciclo model.generate() com transformers serve um pedido de cada vez e reserva memória para o pior caso. Os servidores de inferência resolvem isto com três ideias:

  • Continuous batching: em vez de esperar que um lote inteiro termine, o servidor junta e retira pedidos do lote a cada passo de geração. Um pedido curto não fica preso atrás de um longo e a GPU está sempre cheia.
  • PagedAttention: o KV cache é dividido em blocos pequenos, atribuídos à medida que o texto cresce, como a memória virtual de um sistema operativo. Quase não há desperdício, o que permite muitos mais pedidos em simultâneo (vê a demo acima).
  • API compatível com a da OpenAI: o mesmo cliente que usas para os modelos da API funciona com o teu modelo, incluindo saídas JSON com esquema.

Mais rápido: speculative decoding e prefix caching

  • Speculative decoding: um modelo pequeno (ou cabeças extra do próprio modelo, como no EAGLE e no Medusa, ou n-gramas do prompt) propõe vários tokens e o modelo grande verifica-os todos num só passo. Quando acerta, gera vários tokens pelo custo de um. O resultado é idêntico ao do modelo grande; só muda a velocidade.
  • Prefix caching: pedidos que começam pelo mesmo texto (o mesmo system prompt, os mesmos exemplos few-shot, o mesmo documento) reaproveitam o KV cache desse prefixo. É a versão local do prompt caching das APIs: põe o que é fixo no início do prompt.
  • KV cache quantizado (FP8) e atenção com menos cabeças KV (GQA, MLA nos modelos DeepSeek) reduzem a memória por token e permitem contextos e lotes maiores.
  • Separar prefill e decode em GPUs diferentes é o que fazem os maiores serviços; só compensa a escala muito grande.

Da GPU à API: FastAPI, Docker e deploy

O servidor de inferência não deve ficar exposto diretamente. À frente pões uma API tua que valida pedidos, aplica o prompt certo, verifica a resposta e regista métricas:

@app.post("/classificar")
async def classificar(pedido: Pedido, chave: str = Depends(autenticar)) -> Resposta:
    if (r := cache.get(chave_de(pedido.texto))):
        return r
    saida = await chamar_vllm(pedido.texto)          # httpx assíncrono, timeout curto
    extracao = validar(saida) or await fallback(pedido.texto)
    registar_metricas(...)
    return extracao

Arrancar um contentor com um modelo pode demorar de 30 segundos a vários minutos (cold start). Para tráfego interativo, mantém pelo menos uma réplica ligada ou usa uma API de modelos para o tráfego inicial.

Gateways, cache, limites e custos

  • Gateway de modelos (LiteLLM Proxy, Portkey, OpenRouter, Cloudflare AI Gateway): uma porta única para vários fornecedores e modelos próprios, com chaves por equipa, orçamentos, fallback e registo centralizado.
  • Cache exata: o mesmo texto devolve a mesma resposta sem chamar o modelo. Barata e segura para tarefas deterministas como a nossa.
  • Cache semântica: pedidos parecidos (embedding próximo) reaproveitam a resposta. Poupa mais, mas pode devolver a resposta de uma pergunta diferente; usa um limiar alto e só onde um erro é barato.
  • Rate limiting: limites por chave (pedidos e tokens por minuto) protegem a GPU e o orçamento de um cliente com um ciclo infinito.
  • Encaminhamento por custo: pedidos fáceis para o modelo pequeno, difíceis ou com baixa confiança para um grande.

No use case fazemos uma versão mínima: a API grava cada pedido em SQLite e um painel mostra latência, débito, custo e distribuição das categorias.

Exercício: o p95 da latência triplicou desde ontem, sem alterações no código. Onde procuras?

Primeiro na carga: mais pedidos por segundo ou pedidos mais longos (fila do vLLM, uso do KV cache, tamanho médio do prompt). Depois na infraestrutura: menos réplicas, GPU diferente, outro processo na mesma GPU. Depois na cache: a taxa de acerto caiu? Por fim no fallback: se o modelo começou a produzir respostas inválidas, cada pedido faz duas chamadas. As métricas por componente dizem-te qual destas é, sem adivinhar.

Resumo

Servir um LLM bem é sobretudo gerir memória: os pesos e o KV cache de cada pedido têm de caber na GPU. A quantização (FP8, AWQ, GPTQ, GGUF) reduz os pesos para metade ou um quarto com pouca perda de qualidade, que tens de medir na tua tarefa. Servidores como o vLLM e o SGLang usam continuous batching e PagedAttention para atender dezenas de pedidos em simultâneo na mesma GPU, e expõem uma API compatível com a da OpenAI. À volta do modelo constróis uma API (FastAPI) em contentores (Docker), com cache, limites de pedidos, fallback e métricas de latência, custo e qualidade, porque em produção o que não medes degrada sem aviso.
