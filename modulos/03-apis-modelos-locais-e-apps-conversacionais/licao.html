Como funciona uma API de chat

Todas as APIs de chat seguem o mesmo modelo: envias a conversa inteira como uma lista de mensagens com papéis (system, user, assistant) e recebes a mensagem seguinte do assistente. O servidor não guarda estado entre pedidos. Para continuar uma conversa, voltas a enviar todo o histórico.

from anthropic import Anthropic

client = Anthropic()                 # lê ANTHROPIC_API_KEY do ambiente
historico = [
    {"role": "user", "content": "Olá! Fazem entregas nos Açores?"},
    {"role": "assistant", "content": "Sim, entregamos em todas as ilhas, em 3 a 5 dias úteis."},
    {"role": "user", "content": "E quanto custa?"},     # só faz sentido com o contexto anterior
]
r = client.messages.create(
    model="claude-haiku-5-5",
    max_tokens=300,
    system="És o assistente da Loja Lusa. Responde em português de Portugal.",
    messages=historico,
)
print(r.content[0].text)
print(r.usage.input_tokens, r.usage.output_tokens)
ParâmetroPara que serve
modelQual o modelo. Fixa a versão em produção para evitar mudanças silenciosas.
max_tokensLimite da resposta. Se for atingido, a resposta vem cortada (stop_reason = "max_tokens").
systemInstruções persistentes e personalidade.
temperatureVariedade da resposta (lição M01). Atenção: os modelos Claude mais recentes já não aceitam este parâmetro (a API devolve erro) e usam uma amostragem fixa; continua a existir noutros fornecedores e nos modelos locais.
stop_sequencesTexto que faz parar a geração.

A OpenAI usa o mesmo conceito com nomes ligeiramente diferentes (client.chat.completions.create, a mensagem de sistema vai dentro da lista). Muitos servidores locais e fornecedores de modelos abertos implementam a API da OpenAI, por isso o mesmo SDK serve para falar com eles mudando só o base_url.

Streaming, erros e novas tentativas

Uma resposta de 500 tokens pode demorar 5 a 15 segundos. Com streaming, o texto aparece à medida que é gerado e o utilizador vê o primeiro token em menos de um segundo. A métrica que interessa à experiência é o time to first token (TTFT).

with client.messages.stream(model="claude-haiku-5-5", max_tokens=500,
                            messages=historico) as stream:
    for pedaco in stream.text_stream:
        print(pedaco, end="", flush=True)

Em produção, as chamadas falham. Prepara-te para:

  • 429 (rate limit): excedeste pedidos ou tokens por minuto. Espera e tenta de novo.
  • 500, 529 (sobrecarga): problema do lado do fornecedor. Tenta de novo com espera crescente.
  • 400: o pedido está errado (por exemplo, contexto acima do limite). Não adianta repetir.
  • Timeouts: define-os explicitamente.

Os SDKs oficiais já fazem algumas tentativas com backoff exponencial (max_retries). Para lógica própria, a biblioteca tenacity é a escolha habitual. Em sistemas críticos, configura um fornecedor alternativo para quando o principal está em baixo.

Modelos locais: Ollama, llama.cpp e transformers

Correr um modelo na tua máquina dá privacidade total (os dados nunca saem), custo marginal zero e funcionamento sem internet. Em troca, a qualidade é menor que a dos melhores modelos fechados e precisas de hardware adequado.

Regra prática para memória: um modelo quantizado a 4 bits precisa de cerca de 0,6 GB por mil milhões de parâmetros, mais o KV cache. Um modelo de 7-8B corre bem num portátil com 16 GB; um de 70B precisa de 48 GB ou mais.

Uma interface para todos os fornecedores: LiteLLM

Cada fornecedor tem o seu SDK. O LiteLLM traduz uma única chamada no formato da OpenAI para mais de cem fornecedores, incluindo Ollama. Mudar de modelo passa a ser mudar uma string, o que facilita comparar qualidade e custo e ter alternativas.

from litellm import completion

for modelo in ["anthropic/claude-haiku-5-5", "openai/gpt-4.1-mini", "ollama/qwen2.5:7b"]:
    r = completion(model=modelo, messages=[{"role": "user", "content": "Capital dos Açores?"}])
    print(modelo, "→", r.choices[0].message.content, r.usage.total_tokens)
Na prática

O LiteLLM também tem um modo proxy (um servidor) que centraliza chaves, limites de gasto por equipa e registo de pedidos. Voltamos a ele no módulo 12.

Memória de conversa

Como o servidor não guarda estado, a «memória» é a tua aplicação a decidir que mensagens enviar. O histórico cresce a cada volta e, com ele, o custo e a latência. Estratégias principais:

  • Histórico completo: simples, mas o custo cresce com o quadrado do número de voltas (cada volta reenvia todas as anteriores).
  • Janela deslizante: mantém só as últimas N mensagens ou os últimos N tokens. Barato, mas esquece o início.
  • Resumo: quando o histórico passa de um limite, pede ao modelo um resumo das mensagens antigas e substitui-as por ele.
  • Memória persistente: extrai factos importantes (nome, preferências, encomendas) para uma base de dados e injeta-os no system prompt em conversas futuras.

Interfaces com Gradio, Streamlit e Chainlit

Para demos, protótipos internos e portfólio, não precisas de escrever frontend:

import gradio as gr
from litellm import completion

def responder(mensagem, historico):
    msgs = historico + [{"role": "user", "content": mensagem}]
    texto = ""
    for pedaco in completion(model="anthropic/claude-haiku-5-5", messages=msgs, stream=True):
        texto += pedaco.choices[0].delta.content or ""
        yield texto                                  # streaming na interface

gr.ChatInterface(responder, type="messages", title="Loja Lusa").launch()

Exercício: quanto custa uma conversa de 20 voltas com histórico completo, se cada mensagem tiver 100 tokens?

Na volta k enviamos cerca de 2k−1 mensagens (todas as anteriores mais a nova). A soma de 1 a 20 de (2k−1)·100 = 100·20² = 40 000 tokens de entrada, contra 2 000 se cada volta enviasse só a mensagem nova. É o crescimento quadrático que justifica janelas, resumos e prompt caching.

Resumo

As APIs de LLM recebem uma lista de mensagens e devolvem a próxima, e uma aplicação real precisa de streaming, novas tentativas com backoff e controlo de custos. Modelos abertos correm localmente com Ollama ou llama.cpp, com privacidade total e custo marginal zero, em troca de menos qualidade e de hardware próprio. O LiteLLM dá uma interface única para dezenas de fornecedores. Como os modelos não têm memória, é a aplicação que gere o histórico, com janela deslizante, resumo ou memória persistente. Gradio e Streamlit transformam tudo isto numa interface em poucas linhas.
