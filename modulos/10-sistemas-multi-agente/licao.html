Porquê vários agentes

No módulo 8 construíste um agente: um LLM com ferramentas, em ciclo. Ele começa a falhar em tarefas longas por três razões. O contexto enche: cada resultado de ferramenta fica na conversa e, ao fim de dezenas de passos, o modelo perde o fio. As instruções competem: um único system prompt que explica pesquisa web, SQL, revisão e redação fica longo e ambíguo. E o trabalho é sequencial: cinco pesquisas independentes esperam umas pelas outras.

Um sistema multi-agente responde a isto dividindo o trabalho. Cada agente tem uma tarefa estreita, um prompt curto, só as ferramentas de que precisa e um contexto limpo. Um agente principal coordena e recebe só os resultados condensados.

A ideia central

Um subagente funciona como compressão: lê 30 páginas e devolve 10 linhas com as fontes. O agente principal raciocina sobre resumos, não sobre o material bruto.

Arquiteturas: orquestrador, supervisor, hierarquias e handoffs

ArquiteturaComo funcionaBom para
Orquestrador-trabalhadoresUm agente divide a tarefa, lança trabalhadores (muitas vezes em paralelo) e sintetiza os resultadosPesquisa, análise de muitos documentos, revisão de código por ficheiro
SupervisorUm agente escolhe, a cada passo, qual especialista age a seguir, até dar a tarefa por concluídaFluxos em que a ordem depende do que acontece (apoio técnico, operações)
HierarquiaSupervisores de supervisores: cada equipa tem o seu coordenadorSistemas grandes com domínios distintos; raramente necessário
HandoffsO agente ativo passa o controlo (e a conversa) a outro agente, que passa a falar com o utilizadorAssistentes com triagem: receção, faturação, devoluções
Avaliador-otimizadorUm agente produz, outro critica, o primeiro corrigeTextos, código ou relatórios com critérios de qualidade claros

Na prática, implementas estas arquiteturas com o próprio ciclo de tool use (um subagente é uma ferramenta cuja implementação chama outro agente) ou com frameworks: LangGraph (grafos com estado, o que usamos aqui), OpenAI Agents SDK (handoffs nativos), CrewAI (equipas com papéis), Google ADK, Microsoft Agent Framework (sucessor do AutoGen) e o Claude Agent SDK (subagentes). Os conceitos são os mesmos; muda a ergonomia.

Deep research: planear, pesquisar em paralelo e sintetizar

As funcionalidades de «deep research» dos assistentes comerciais seguem o mesmo esqueleto: planear subperguntas, investigá-las em paralelo, verificar e escrever um relatório com citações. É também o use case deste módulo, uma equipa de pesquisa de mercado para a Loja Lusa:

  • Plano explícito e estruturado: o planeador devolve uma lista de tarefas com a fonte de cada uma (web ou dados internos), validada com Pydantic. Um plano em texto livre é difícil de distribuir.
  • Instruções completas para cada trabalhador: o subagente não vê a conversa do orquestrador. Diz-lhe o objetivo, o formato de saída, as fontes aceitáveis e quando parar.
  • Esforço proporcional: uma pergunta factual precisa de um investigador e duas pesquisas; uma análise de mercado, de quatro ou cinco. Diz ao planeador como escalar.
  • Citações verificáveis: cada afirmação no relatório aponta para uma fonte que o revisor viu. É a mesma ideia de fidelidade do módulo 7.

Quanto custa e quão fiável é

Mais agentes trazem paralelismo, mas também mais tokens e mais pontos de falha. Se cada passo de um agente tem uma probabilidade p de correr bem, uma tarefa com n passos sai certa com probabilidade pⁿ. Experimenta:

Repara em três coisas. A fiabilidade cai depressa com o número de passos, por isso tarefas curtas e bem delimitadas por trabalhador são melhores do que poucas tarefas longas. Um revisor que deteta falhas e repete recupera muita fiabilidade. E o paralelismo poupa tempo, não tokens: a Anthropic reportou que o seu sistema de pesquisa multi-agente gasta cerca de 15 vezes mais tokens do que uma conversa normal.

Estado, checkpoints e aprovação humana com LangGraph

No LangGraph descreves o sistema como um grafo: os nós são funções (um agente, um passo de código), as arestas dizem o que vem a seguir e um estado tipado circula entre nós. Cada nó devolve só as chaves que quer alterar; um reducer diz como juntar atualizações (por exemplo, acrescentar a uma lista em vez de substituir).

from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send, interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

class Estado(TypedDict):
    pergunta: str
    tarefas: list[dict]
    achados: Annotated[list[dict], operator.add]   # cada investigador acrescenta
    decisao_humana: str
    relatorio: str

def planear(s):      return {"tarefas": planeador(s["pergunta"])}
def investigar(t):   return {"achados": [investigador(t)]}        # recebe só a sua tarefa
def aprovar(s):      return {"decisao_humana": interrupt({"achados": s["achados"]})}
def escrever(s):     return {"relatorio": redator(s)}

def distribuir(s):   # fan-out: um Send por tarefa, corre em paralelo
    return [Send("investigar", t) for t in s["tarefas"]]

g = StateGraph(Estado)
for nome, f in [("planear", planear), ("investigar", investigar), ("aprovar", aprovar), ("escrever", escrever)]:
    g.add_node(nome, f)
g.add_edge(START, "planear")
g.add_conditional_edges("planear", distribuir, ["investigar"])
g.add_edge("investigar", "aprovar")
g.add_edge("aprovar", "escrever")
g.add_edge("escrever", END)
app = g.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "coimbra-2026"}}
app.invoke({"pergunta": "Abrir loja em Coimbra?"}, cfg)   # para em interrupt()
app.invoke(Command(resume="ok, mas ignora a fonte 3"), cfg)   # retoma do checkpoint
  • Checkpoints: com um checkpointer (memória, SQLite, Postgres), o estado é gravado depois de cada passo, identificado por thread_id. Se o processo cair a meio, retomas do último passo concluído em vez de pagar tudo outra vez. Também podes ver o histórico (get_state_history) e criar um ramo a partir de um passo anterior (update_state) para experimentar outro caminho sem repetir o que já foi feito.
  • Human-in-the-loop: interrupt() para a execução, grava o estado e devolve ao chamador o que queres mostrar. A pessoa pode demorar horas; retomas com Command(resume=...) e o valor passa a ser o retorno de interrupt().
  • Limites: o LangGraph tem um recursion_limit (número máximo de passos do grafo). Junta-lhe um orçamento de tokens no estado e um número máximo de rondas de revisão.
Onde pôr a pessoa

Pausa antes de ações irreversíveis ou caras (enviar, publicar, pagar, lançar 20 pesquisas) e nos pontos em que um erro se propaga (validar o plano ou os achados antes do relatório). Pedir aprovação em todos os passos ensina a pessoa a clicar «sim» sem ler.

Avaliar agentes

Um agente pode chegar à resposta certa por um caminho errado (por sorte, ou ignorando uma fonte obrigatória) ou falhar a resposta com um caminho quase perfeito. Por isso avalia-se em duas camadas:

CamadaO que verificasComo
ResultadoA resposta final está correta e completa? As citações suportam as afirmações?Comparação com resposta de referência, testes, LLM como juiz com rubrica (módulo 7)
TrajetóriaChamou as ferramentas certas? Respeitou as regras (usar dados internos, pedir aprovação)? Quantos passos e tokens gastou?Verificações determinísticas sobre o registo da execução

Os agentes são estocásticos: a mesma tarefa pode correr bem numa execução e mal na seguinte. Repete cada tarefa várias vezes e distingue duas métricas: pass@k (acertou pelo menos uma vez em k, útil quando uma pessoa escolhe a melhor tentativa) e pass^k (acertou todas as k vezes, o que importa em produção). Um agente com 60 % de sucesso por tentativa tem pass@3 de 94 % mas pass^3 de apenas 22 %.

Benchmarks públicos que vais ver citados: SWE-bench Verified (resolver issues reais de repositórios Python, verificado por testes), GAIA (perguntas de assistente geral que exigem pesquisa, ficheiros e raciocínio em vários passos), τ-bench (agentes de apoio ao cliente com políticas e utilizadores simulados, onde surgiu o pass^k), OSWorld (usar um computador) e BrowseComp (encontrar informação difícil na web). Servem para comparar modelos; para o teu sistema, precisas do teu próprio conjunto de tarefas.

Quando um só agente chega

A regra prática: começa com um só agente bem desenhado e só divide quando medires um problema que a divisão resolve.

SinalUm agenteVários agentes
Estrutura da tarefaPassos dependentes uns dos outrosPartes independentes que podem correr em paralelo
ContextoCabe confortavelmente numa conversaCada parte lê muito material que as outras não precisam
Ferramentas e instruçõesPoucas e coerentesMuitas, de domínios distintos, que confundem o modelo
Valor da tarefaBaixo ou com orçamento apertadoAlto o suficiente para pagar 5 a 15 vezes mais tokens
Partilha de contextoTodas as decisões precisam de tudo o que já se sabe (por exemplo, escrever código coerente)Cada parte decide sozinha com instruções claras

Programação é um bom contra-exemplo: as decisões num ficheiro dependem das decisões noutros, e agentes paralelos a escrever código produzem peças que não encaixam. Pesquisa é o caso favorável: cinco subperguntas sobre um mercado investigam-se de forma independente.

Exercício: desenha um sistema multi-agente para rever contratos de fornecedores.

Uma proposta: um orquestrador recebe o contrato e lança trabalhadores em paralelo, um por tema (prazos e renovação, penalizações, proteção de dados, foro e lei aplicável), cada um com as cláusulas relevantes e uma checklist da política da empresa. Um revisor confirma que cada problema apontado cita a cláusula exata. Uma pessoa do jurídico aprova antes de o relatório ser enviado ao fornecedor. Avaliação: um conjunto de contratos com problemas conhecidos, medindo quantos são encontrados (recall), quantos alertas são falsos e o pass^3.

Resumo

Um sistema multi-agente divide uma tarefa longa entre agentes especializados, coordenados por um orquestrador, um supervisor ou passagens de controlo (handoffs). Compensa quando a tarefa se divide em partes independentes que podem correr em paralelo, cada uma com o seu contexto, como na pesquisa aprofundada; o preço é muito mais tokens, mais latência de coordenação e falhas que se acumulam. O LangGraph modela o sistema como um grafo com estado partilhado, checkpoints que permitem retomar e pausas para aprovação humana. Avalia-se pelo resultado e pela trajetória, repetindo cada tarefa várias vezes, porque um agente que acerta uma vez em três não está pronto para produção.
